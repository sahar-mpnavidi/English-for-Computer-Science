# Lesson 12: Websites, Apps, and APIs

## Level: B1
## Time: 90–120 minutes

> **درس ۱۲ — وب‌سایت‌ها، اپ‌ها و APIها**
> **نکتهٔ گرامری:** افعال وجهی *should / must / have to* · *might / may* · تفاوت *mustn’t* با *don’t have to*

### 1. Lesson Objectives / اهداف درس

- اجزای یک وب‌سایت (صفحهٔ اصلی، ناوبری، چیدمان، فرم) و اجزای رابط کاربری را به انگلیسی نام ببرید.
- توضیح دهید API چیست و یک برنامه چگونه با یک سرویس وب گفت‌وگو می‌کند.
- با *should* توصیه، با *must* الزام و با *might* احتمال را بیان کنید.
- تفاوت *mustn’t* (ممنوعیت) و *don't have to* (نبود الزام) را در جمله‌های درست نشان دهید.
- پنج قاعدهٔ انگلیسی برای ساختن یک وب‌سایت خوب بنویسید.

### 3. Reading / متن اصلی

**عنوان متن: Three Faces of One Service (سه چهرهٔ یک سرویس)**

**[1]** A website, an app, and an API are often three faces of the same service. People see a website in a browser, they touch an app on a phone, and a program speaks to the service through an API. All three must work with the same data, and all three must be easy to use.

**[2]** A website begins with a homepage, and a marketing page is often called a landing page. The navigation tells visitors where they can go, and the layout decides where every part sits on the screen. A clear navigation is more important than a beautiful picture.

**[3]** Inside a page there are many small parts: a footer at the bottom, a sidebar on the side, and sometimes a banner with an offer. A form has a field for each answer, and a dropdown, a checkbox, and a slider are three common ways to collect them. A placeholder shows what to write, and a tooltip explains a part.

**[4]** Designers do not start with the final page. First they draw a wireframe: a simple plan with boxes. Then they build a mockup with the real style, colours, fonts, and media, and later they make a prototype that people can click. The logo, the theme, and every widget must fit together.

**[5]** Most visitors now use a phone, so a modern website must be responsive and mobile-friendly. A responsive design changes with the viewport, and a breakpoint decides when the layout moves. Good contrast helps people with weak eyes, and accessibility and usability are not extra features; they are part of the job.

**[6]** What makes a page easy to use? An intuitive design and a user-friendly workflow. A cluttered page with fifty buttons is bad; a minimal page with three clear actions is good. An interactive element should give an answer in a second, and a preview must show the result before the user saves it.

**[7]** Should you build an app or a website? A native app works better on one system, and a cross-platform app is cheaper because one team writes it once. Every app must be compatible with the systems that your users have, and it must be supported with new versions. A beta version is experimental, so only testers should use it.

**[8]** What is an API? An API is a door for programs. One program sends a request to a web service and receives a response. Most modern services use REST; some use GraphQL, which lets the caller ask for exactly what it needs. The answer often comes as JSON, or sometimes as older XML.

**[9]** How does one API call work? The client sends a query with a method such as GET or POST, and the server answers with a collection of resources. Long lists arrive in pages, so pagination keeps every answer small, and a batch request can send many changes together.

**[10]** Security is not optional in an API. The server must check every call, so authorization decides what a token can do. The service should send its certificate, and it should store passwords as a hash, never as a simple text. A third-party program must follow the same specification as everybody else.

**[11]** Teams never test directly in the real system. They work in a sandbox, then in a staging environment that looks like the real one, and only then in production. A slow rollout gives the team time, and a rollback brings the old version back in one minute. Every change appears in the changelog.

**[12]** Behind the door there are many workers. Middleware sits between the request and the answer, and a handler does the small job of one route. A queue holds the heavy work, a worker finishes it later, and a scheduler starts the same job every night. A proxy and a CDN keep the service fast. A webhook tells another service that something has happened.

**[13]** Data must have a shape. A schema describes every part of a resource: its name, its type, and the rules of the collection. When the schema changes, old programs can break, so a good team keeps the change small and tells everybody before the release. The shape of the data is a contract between teams.

**[14]** A web project needs a clear process. Every requirement should be written, and every sprint should end with something that works. The team keeps a backlog of work, a tracker for issues, and a milestone for each month. Feedback from users is the most useful input of all.

**[15]** How do teams measure a website? Telemetry shows what users really do, not what they say. Three numbers matter most: conversion, engagement, and retention. Onboarding is the first step of retention, because a new user who does not understand the page in one minute may never come back.

**[16]** Rules are part of a good website. The terms must be clear, and the page should ask for consent before it collects personal data. A form must not hide its purpose. If a page is not accessible, some users cannot use it at all, and that is a failure, not a small problem.

**[17]** Mina built a small website for her class project. She had to choose a layout, and she had to write a landing page with a clear navigation. Her first page was cluttered, so her teacher said that she should simplify it. She did not have to change the whole design.

**[18]** Then she added a small API. She had to learn JSON and one method, GET, and she had to test every query in the sandbox before production. Her program sends a request, receives a response, and shows a preview of the answer. She might add pagination later, because the collection will grow.

**[19]** What should a beginner do? You should start with one page, not with twenty. You should not copy a whole design; a minimal page teaches more. You must test your work on a real phone, and you must not hide the important parts of the navigation. You do not have to know everything: a small prototype is a good start.

**[20]** What are the most common mistakes? A team might forget the mobile viewport, so the page looks broken on a phone. Another team might forget accessibility. A third team might publish a beta version in production by mistake, or forget the rollback plan. Most of these mistakes are cheap to fix — before the release.

**[21]** What does the future hold? A website might be generated from the same schema as the app, and one API might serve ten different clients. Developers should learn the common ideas, not only one framework: HTTP methods, JSON, authorization, and accessibility. Tools will change, but the checks will stay.

**[22]** One idea is easy to forget: a website is a contract with its users. The terms, the consent, and the language must be clear. A button that says "Send" must send, and a preview must show what will happen. If the experience is intuitive, nobody notices the design; if it is not, everybody notices it.

**[23]** So, which one should you build first? If you have a small idea, you should start with a website: it is faster to publish and easier to test. When the idea works, you can add an app. The API should come with the first version, because every other door will need it later. Start small, measure early, and change carefully.

**[24]** An API without documentation is a locked door. A specification should say what every resource needs, what the response looks like, and which errors are possible. A good example is worth a page of text. Every team member should be able to copy the example and see an answer in a minute.

**[25]** Most teams do not build everything. A third-party service may give them payment, maps, or email, and a webhook may send a message when something changes. The team must check the terms of that service, and they should read its specification before they write one line of code.

**[26]** Should you make the page smaller or the server faster? Measure first. Telemetry and a tracker can show which resource is slow, and a scheduler can repeat the heavy job at night when the queue is empty. A small improvement in the first screen is usually worth more than a big change inside the code.

**[27]** Accessibility is a legal and human duty, not a favour. A form must connect every field to a label, a picture should have a text description, and the contrast must be strong enough. For an accessible page, a screen reader reads the navigation and every field in the correct order.

**[28]** Trust is the real product. A user who does not trust a page will not send a password or a card number. The page should explain why it needs each field, and it must not share personal data without consent. Every beta version should show a short notice, and every preview should be honest.

**[29]** Websites, apps, and APIs are one service with three faces. A website lives on a page and must be responsive and accessible; an app lives on a device and must be compatible; an API lives behind the door and must be clear, secure, and documented. You should learn all three, because a good product needs all three.

**[۱]** یک وب‌سایت، یک اپ و یک API اغلب سه چهرهٔ یک سرویس هستند. مردم وب‌سایت را در مرورگر می‌بینند، اپ را روی گوشی لمس می‌کنند و یک برنامه از طریق API با سرویس حرف می‌زند. هر سه باید با دادهٔ یکسان کار کنند و هر سه باید استفاده‌شان آسان باشد.

**[۴]** طراحان با صفحهٔ نهایی شروع نمی‌کنند. نخست یک طرح اولیه می‌کشند: نقشه‌ای ساده با جعبه‌ها. بعد یک ماکاپ با سبک، رنگ‌ها و قلم‌های واقعی می‌سازند و بعدتر یک نمونهٔ اولیه که مردم می‌توانند روی آن کلیک کنند. لوگو، تم و هر ویجت باید با هم هماهنگ باشند.

**[۸]** API چیست؟ API دروازه‌ای برای برنامه‌هاست. یک برنامه درخواستی به یک سرویس وب می‌فرستد و پاسخی دریافت می‌کند. بیشتر سرویس‌های امروزی از REST استفاده می‌کنند؛ بعضی از GraphQL که به فراخوان اجازه می‌دهد دقیقاً همان چیزی را بخواهد که لازم دارد. پاسخ اغلب در قالب JSON می‌آید و گاهی در قالب قدیمی‌تر XML.

**[۱۰]** امنیت در یک API اختیاری نیست. سرور باید هر فراخوانی را بررسی کند، پس مجوز دسترسی تعیین می‌کند یک توکن چه کاری می‌تواند انجام دهد. سرویس باید گواهی خود را بفرستد و رمزهای عبور را به‌صورت درهم‌ساز ذخیره کند، نه متن ساده. یک برنامهٔ شخص سوم هم باید همان مشخصات فنی را رعایت کند که بقیه.

**[۱۱]** تیم‌ها هرگز مستقیم در سامانهٔ واقعی آزمون نمی‌کنند. در یک محیط آزمایش کار می‌کنند، بعد در محیط پیش‌انتشار که شبیه محیط واقعی است و تنها پس از آن در محیط عملیاتی. انتشار تدریجی به تیم زمان می‌دهد و بازگردانی نسخه در یک دقیقه نسخهٔ قدیمی را برمی‌گرداند. هر تغییر در فهرست تغییرات می‌آید.

**[۱۹]** یک مبتدی باید چه کار کند؟ باید با یک صفحه شروع کنید، نه با بیست صفحه. نباید یک طرح کامل را رونوشت کنید؛ یک صفحهٔ کمینه بیشتر یاد می‌دهد. باید کار خود را روی یک گوشی واقعی آزمون کنید و نباید بخش‌های مهم ناوبری را پنهان کنید. لازم نیست همه‌چیز را بدانید: یک نمونهٔ اولیهٔ کوچک شروع خوبی است.

**[۲۷]** دسترس‌پذیری یک وظیفهٔ قانونی و انسانی است، نه لطف. یک فرم باید هر فیلد را به یک برچسب وصل کند، یک تصویر باید توضیح متنی داشته باشد و تباین باید به‌اندازهٔ کافی قوی باشد. در یک صفحهٔ دسترس‌پذیر، نرم‌افزار خوانندهٔ صفحه ناوبری و هر فیلد را به ترتیب درست می‌خواند.

**خلاصهٔ فارسی متن:**

این درس نشان می‌دهد وب‌سایت، اپ و API سه چهرهٔ یک سرویس‌اند و هر سه باید با دادهٔ مشترک کار کنند. یک وب‌سایت از صفحهٔ اصلی و صفحهٔ ورودی آغاز می‌شود، ناوبری و چیدمان آن را می‌سازند و اجزای کوچکی مانند پاصفحه، نوار کناری، بنر، فیلد، فهرست بازشو، کادر انتخاب، لغزنده، جاگیر متن و راهنمای شناور در آن به کار می‌رود. طراحان نخست طرح اولیه و ماکاپ می‌سازند و سپس نمونهٔ اولیه؛ سبک، قلم، تباین و لوگو هویت صفحه را می‌سازند. صفحهٔ امروزی باید واکنش‌گرا و مناسب موبایل باشد، با محدودهٔ دید و نقطهٔ شکست، و دسترس‌پذیری و کاربردپذیری بخشی از کار است، نه ویژگی اضافه.

در سمت برنامه، یک API دروازه‌ای برای برنامه‌هاست: کلاینت یک پرس‌وجو با یک متد می‌فرستد و پاسخ در قالب JSON یا XML می‌آید؛ REST و GraphQL دو سبک رایج‌اند، صفحه‌بندی پاسخ‌های بلند را کوچک نگه می‌دارد و درخواست دسته‌ای چند تغییر را با هم می‌فرستد. امنیت با مجوز دسترسی، گواهی و درهم‌ساز تأمین می‌شود و شخص سوم هم باید همان مشخصات فنی را رعایت کند. پشت صحنه از میان‌افزار، پردازشگر مسیر، صف، کارگر پردازش، زمان‌بند، پروکسی، CDN و وب‌هاک استفاده می‌کند و شمای داده قراردادی میان تیم‌هاست.

کار تیمی با نیازمندی، دورهٔ کاری کوتاه، فهرست کارهای عقب‌افتاده، نقطهٔ عطف، پیگیری مسئله‌ها و بازخورد پیش می‌رود و کیفیت با سنجش از دور، نرخ تبدیل، میزان تعامل، نگهداشت کاربر و آشناسازی سنجیده می‌شود. محیط‌های آزمایش، پیش‌انتشار و عملیاتی، همراه با انتشار تدریجی و بازگردانی نسخه، خطر انتشار را کم می‌کنند و شرایط استفاده، رضایت کاربر و پیش‌نمایش صادقانه اعتماد می‌سازند. در پایان، درس با افعال وجهی به خواننده توصیه و الزام می‌دهد: باید با یک صفحه شروع کنی، نباید طرح را رونوشت کنی، و لازم نیست همه‌چیز را بدانی.

### 7. Grammar Focus / نکتهٔ گرامری

**موضوع: افعال وجهی — should / must / have to / might**

**توضیح فارسی:**

افعال وجهی (*should, must, might, may, can*) همیشه با **فعل ساده** می‌آیند: بدون *to* و بدون *-s*. با **should** **توصیه** می‌دهیم (*You should test the page on a phone. / You shouldn't copy the design.*)، با **must** **الزام قوی** یا **ممنوعیت** را بیان می‌کنیم (*The server must check every call. / You mustn't share your token.*)، و با **have to** از **الزام بیرونی** حرف می‌زنیم، یعنی قانونی که از بیرون آمده است (*I have to finish the API tonight.*).

**might / may** **احتمال** را نشان می‌دهند: *The collection might grow. / It may be slow at peak hours.*

**منفی و سؤالی:** منفی با *not* بعد از فعل وجهی ساخته می‌شود (*should not / shouldn't*, *must not / mustn't*, *might not*)، اما *have to* با *do / does* منفی و سؤالی می‌شود (*I don't have to register. / Do I have to register?*). برای سؤال، فعل وجهی به ابتدای جمله می‌آید: *Should I use REST? / Must the server check every call?* پاسخ کوتاه: *Yes, you should. / No, you don't have to.*

**دو تفاوت مهم:** ① **mustn't** یعنی «ممنوع است» ولی **don't have to** یعنی «لازم نیست»: *You mustn't share the token.* (اشتراکش ممنوع) در برابر *You don't have to share the token.* (لازم نیست به اشتراک بگذاری). ② **must** بیشتر الزام درونی یا گوینده است و **have to** الزام بیرونی: *I must learn this.* / *I have to send the report today.*

دو خطای رایج فارسی‌زبانان: ① آوردن *to* بعد از فعل وجهی («She must to test» ← ~~must to test~~ / *must test*)؛ ② اضافه کردن *-s* («He shoulds check» ← ~~shoulds~~ / *should check*).

**جدول ۱ — کاربرد افعال وجهی:**

| فعل وجهی | کاربرد | نمونه |
|---|---|---|
| should / shouldn't | توصیه | You should test it on a phone. |
| must / mustn't | الزام قوی / ممنوعیت | The server must check every call. |
| have to / don't have to | الزام بیرونی / نبود الزام | I have to finish it tonight. |
| might / may | احتمال | The collection might grow. |

**جدول ۲ — منفی، سؤالی و پاسخ کوتاه:**

| ساخت | نمونه |
|---|---|
| should not (shouldn't) | You shouldn't copy the whole design. |
| must not (mustn't) | You mustn't share your API token. |
| do not have to | You don't have to write the whole app. |
| سؤالی | Should I use REST? / Do I have to register? |
| پاسخ کوتاه | Yes, you should. / No, you don't have to. |

**جدول ۳ — دو تفاوت مهم:**

| دو فعل | تفاوت | نمونه |
|---|---|---|
| mustn't / don't have to | ممنوع است / لازم نیست | You mustn't share it. / You don't have to share it. |
| must / have to | الزام درونی / الزام بیرونی | I must learn this. / I have to send it today. |
| should / must | توصیه / الزام | You should check it. / You must check it. |

### 9. Writing Task / تمرین نگارش

**موضوع: My Rules for a Good Website — قاعده‌های من برای یک وب‌سایت خوب**

قاعده‌های خود را برای ساختن یک وب‌سایت خوب بنویسید. این موارد را رعایت کنید:

- سه توصیه با *should* (طراحی، محتوا، آزمون).
- دو الزام با *must* و یک ممنوعیت با *mustn’t*.
- دو جمله با *might* یا *may* (احتمال).
- یک جمله با *don't have to* که بگوید چه چیزی ضروری نیست.

**شرایط نگارش:**

- نوشته بین **۱۲۰ تا ۲۰۰ واژه** باشد.
- دست‌کم **۵ جمله با should**، **۳ جمله با must / mustn’t** و **۲ جمله با might / may** داشته باشد.
- دست‌کم **۱۰ واژه** از جدول‌های واژگان بخش ۲ استفاده شود.

### 10. Mini Project / پروژهٔ کوچک

**انشا (نیمه‌تحقیقی): گزارش یک وب‌سایت یا API واقعی**

یک وب‌سایت یا اپ یا API را که **خودتان** زیاد استفاده می‌کنید انتخاب کنید و دربارهٔ آن گزارش کوتاهی بنویسید:

- **چهرهٔ وب:** صفحهٔ اصلی و ناوبری آن چگونه است؟ چه اجزایی دارد (پاصفحه، نوار کناری، بنر، فرم، فهرست بازشو)؟
- **واکنش‌گرایی:** آن صفحه روی گوشی چه تفاوتی با رایانه دارد؟ یک نقطهٔ شکست را حدس بزنید.
- **API:** به نشانی مستندات آن سرویس نگاه کنید (اگر در دسترس است) و بنویسید چه سبکی دارد (REST یا GraphQL)، پاسخ در چه قالبی می‌آید، و چه چیزهایی برای احراز هویت لازم است.
- **شکل دستی:** یک **شکل دستی ساده** بکشید که چهار بخش اصلی یک صفحه را نشان دهد (بالا، ناوبری، محتوا، پاصفحه) و هر بخش را برچسب بزنید.
- **قاعده‌ها:** پنج قاعده برای این سرویس بنویسید: دو مورد با *should*، دو مورد با *must / mustn’t* و یک مورد با *might*.
- **پیشنهادها:** دو پیشنهاد برای بهتر شدن تجربهٔ کاربری آن بنویسید.

**شرایط نگارش:**

- گزارش را **دست‌نویس روی کاغذ** بنویسید و در **جلسهٔ بعد** به مدرس تحویل دهید.
- دست‌کم **۲۰۰ واژه** باشد (بدون احتساب شکل).
- دست‌کم **۵ جمله با should**، **۴ جمله با must / mustn’t**، **۲ جمله با might / may** و **۱ جمله با don’t have to** داشته باشد.
- دست‌کم **۱۲ واژه** از جدول‌های واژگان بخش ۲ در گزارش باشد.

**واژه‌های یاری‌دهنده:** homepage · navigation · layout · responsive · accessible · usability · wireframe · API · resource · schema · authorization · pagination

### 11. Did You Know? / آیا می‌دانستید؟

1. **The word "API" has been used since the 1960s, long before the web existed.**
   واژهٔ «API» از دههٔ ۱۹۶۰ به کار می‌رفت، بسیار پیش از آنکه وب وجود داشته باشد.

2. **REST was described in 2000 in a doctoral dissertation, and it became the most common style for web APIs.**
   سبک REST در سال ۲۰۰۰ در یک رسالهٔ دکتری توصیف شد و رایج‌ترین سبک برای APIهای وب شد.

3. **JSON was published in 2001 and slowly replaced XML in most web APIs, because it is shorter and easier to read.**
   قالب JSON در سال ۲۰۰۱ منتشر شد و به‌تدریج در بیشتر APIهای وب جای XML را گرفت، چون کوتاه‌تر و خواناتر است.

4. **GraphQL was released in 2015 and gave clients a way to ask for exactly the fields they need.**
   GraphQL در سال ۲۰۱۵ منتشر شد و به کلاینت‌ها راهی داد تا دقیقاً همان فیلدهایی را بخواهند که لازم دارند.

5. **By 2023, most web traffic was encrypted: industry reports showed that the great majority of pages now use HTTPS.**
   تا سال ۲۰۲۳ بیشتر ترافیک وب رمزنگاری‌شده بود: گزارش‌های صنعت نشان داد اکثریت بزرگ صفحه‌ها امروز از HTTPS استفاده می‌کنند.

6. **A single modern web page can make more than a hundred requests — for images, fonts, scripts, and data — before it is ready.**
   یک صفحهٔ وب امروزی پیش از آماده شدن می‌تواند بیش از صد درخواست بفرستد: برای تصویرها، قلم‌ها، اسکریپت‌ها و داده.

7. **Industry reports in 2023 estimated that more than half of all web APIs use REST, and that JSON appears in the great majority of them.**
   گزارش‌های صنعت در سال ۲۰۲۳ برآورد کردند بیش از نیمی از APIهای وب از REST استفاده می‌کنند و JSON در اکثریت بزرگ آن‌ها به کار می‌رود.

8. **Accessibility standards have existed since 1999, and industry reports in 2023 showed that a large number of popular websites still fail basic accessibility checks.**
   استانداردهای دسترس‌پذیری از سال ۱۹۹۹ وجود دارند و گزارش‌های صنعت در سال ۲۰۲۳ نشان داد شمار زیادی از وب‌سایت‌های محبوب هنوز در بررسی‌های پایهٔ دسترس‌پذیری رد می‌شوند.
